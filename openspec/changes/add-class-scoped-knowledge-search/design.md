## Context

当前应用是基于 Python 标准库 HTTP 服务和 SQLite 的单体应用。`knowledge_entries` 每份材料仅保存一段完整正文，并通过 `material_id`、`class_id` 关联原材料；现有材料列表和详情读取已经使用服务端会话中的 `class_id` 做授权，但尚无分片、相关度检索、索引状态或片段定位。现有 Docker Compose 只承载应用和持久化数据。本设计在不改变既有登录、上传和材料查看契约的前提下增加检索能力，动机见 `proposal.md`，行为契约见 `specs/class-scoped-knowledge-search/spec.md`。

## Goals / Non-Goals

**Goals:**

- 让班级授权同时作用于向量候选查询和关系数据复核，形成双层隔离。
- 让每个命中片段都能稳定回溯到 SQLite 中的知识库条目和原始材料。
- 使检索后端可替换，并为批量回填、失败重试和索引重建保留清晰边界。
- 保持检索 API 的结果结构稳定，不把具体向量数据库的字段暴露给调用方。

**Non-Goals:**

- 不实现大语言模型生成答案、对话记忆、自动摘要或答案质量评估。
- 不实现跨班级共享知识库、多班级联合检索或管理员全局检索。
- 不支持图片 OCR、音视频转写和复杂版面坐标；本次片段定位以文本顺序和字符范围为准。
- 不把向量数据库作为材料正文和权限元数据的唯一事实来源。

## Decisions

1. SQLite 保存权威内容与来源关系，向量数据库只保存可重建的检索索引。

   新增知识片段记录，至少包含 `id`、`knowledge_entry_id`、`material_id`、`class_id`、`ordinal`、`char_start`、`char_end`、`content` 和 `index_status`。向量索引使用片段 ID 作为稳定主键，并携带 `class_id`、`material_id` 等过滤载荷；标题、正文、班级归属和授权关系仍以 SQLite 为准。这样可以从原始材料重建索引，也能在返回结果前用关系数据再次校验来源。

   Alternatives considered: 仅在向量数据库保存正文和来源元数据。该方案查询简单，但会形成第二套权限事实来源，索引载荷陈旧时容易产生越权或错误溯源。

2. 首个实现采用 Qdrant 作为向量索引，并通过检索适配器隔离具体产品。

   Docker Compose 增加 Qdrant 服务；应用侧定义分片写入、删除、按班级过滤查询和健康检查等最小接口。嵌入模型及其版本由服务端配置固定，索引集合记录向量维度和模型版本；调用 API 时只暴露统一的检索结果，不暴露 Qdrant 点或集合结构。

   Alternatives considered: 直接使用 SQLite `LIKE`，无法提供稳定相关度且中文匹配能力有限；SQLite FTS5 部署简单，但默认中文分词和语义近似能力不足。嵌入式向量库减少一个容器，但并发写入、备份和健康检查边界不如独立服务清晰。若部署环境不允许 Qdrant，可实现同一适配器的其他后端，但必须满足相同班级过滤和来源复核规则。

3. 班级过滤在候选检索与结果装配两个阶段强制执行。

   检索服务只从可信会话读取 `class_id`，调用向量数据库时添加精确班级过滤。取得候选片段 ID 后，再用包含 `chunk_id`、`material_id`、`class_id` 和材料可用状态的联合查询装配结果；关系查询不匹配的候选直接丢弃。客户端提交的 `class_id` 不进入检索条件。

   Alternatives considered: 先做全库向量检索，再在应用层过滤。该方案既浪费候选额度，也可能通过结果数量、延迟或日志泄露其他班级信息。

4. 使用确定性文本分片并持久化定位信息。

   首版按段落优先切分，超长段落再按固定字符窗口切分，保留小范围重叠；默认目标长度和重叠大小由服务端配置控制。每个片段保存顺序号与原文字符起止位置，来源展示使用这些稳定字段，不依赖向量数据库生成的摘要。相同内容和配置应产生相同片段顺序，便于测试和重建。

   Alternatives considered: 只按固定字符数切分实现最简单，但会频繁截断语义；只保存片段序号无法精确核对原文位置；使用模型动态分片质量可能更高，但难以复现并增加外部依赖。

5. 索引发布采用“先准备、后整体可见”的状态流转。

   上传解析成功后，在 SQLite 事务中创建全部片段并标记为 `pending`；向量写入全部成功后再将该材料相关片段整体标记为 `ready`。检索结果装配仅接收 `ready` 片段。失败时标记为 `failed` 并允许幂等重试；向量点使用片段 ID 幂等覆盖，避免重复。材料仍可沿用现有页面查看，只有检索可见性受索引状态控制。

   Alternatives considered: 每写入一个向量就立即可检索，会在中途失败时暴露部分材料；把跨 SQLite 与 Qdrant 操作当作单一事务不可行，因为两者没有共享事务管理器。

6. 提供稳定、受保护的检索接口。

   新增 `GET /api/search?q=<query>&limit=<n>`（或等价受保护接口），默认返回有限条结果并设置服务端最大上限。响应包含 `excerpt`、`score` 和 `source`；`source` 至少包含 `material_id`、`material_title`、`chunk_id`、`chunk_ordinal`、`char_start`、`char_end` 与现有受保护材料详情链接。空白查询返回参数错误，无结果返回成功与空数组，后端不可用返回暂时不可用。

   Alternatives considered: 直接返回完整材料正文会增加不必要的数据暴露和响应体积；让前端自行拼接来源会使溯源字段无法由服务端保证一致。

## Risks / Trade-offs

- [Risk] 嵌入模型升级后，新旧向量不可比较。→ Mitigation: 保存模型标识和索引版本，版本变化时创建新集合并完成全量回填后再切换。
- [Risk] Qdrant 过滤载荷错误导致跨班候选。→ Mitigation: 强制添加 `class_id` 过滤，并在 SQLite 结果装配阶段再次校验班级、片段状态和材料状态。
- [Risk] SQLite 已提交但向量写入失败，产生双写不一致。→ Mitigation: 使用 `pending/ready/failed` 状态、幂等片段 ID 和可重试回填任务，只有 `ready` 数据对检索可见。
- [Risk] 中文分片或嵌入模型质量不足导致相关度偏低。→ Mitigation: 选用支持中文的嵌入模型，固定测试语料和期望命中来源，并把分片参数配置化。
- [Risk] 向量数据库增加部署和资源成本。→ Mitigation: 在 Compose 中提供健康检查和持久卷，检索适配器保持可替换，应用启动时验证必要配置。
- [Risk] 相关度分数被误解为统一概率。→ Mitigation: 分数仅用于同次查询排序，不在接口契约中承诺跨模型或跨版本可比较。

## Migration Plan

1. 增加知识片段表、索引状态和必要索引，不改动现有材料与知识库条目的主键。
2. 在 Compose 中部署带持久卷和健康检查的 Qdrant，并配置固定的集合名、嵌入模型标识与向量维度。
3. 对现有 `available` 材料按班级分批分片和写入向量索引；每份材料全部成功后才把其片段标记为 `ready`。
4. 回填验证通过后启用检索 API 和页面入口；发布期间尚未完成回填的材料仍可查看，但不会出现在检索结果中。
5. 回滚时先关闭检索入口，再停止 Qdrant；保留 SQLite 中的原始材料、知识条目和片段记录。向量集合可由权威内容重建，不因回滚删除用户原始材料。
