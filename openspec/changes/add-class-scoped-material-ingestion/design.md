## Context

当前仓库尚未包含应用实现代码或既有主规格，只有 OpenSpec 配置和项目 README。因此本设计以新建能力为前提，约束后续实现必须把权限判断和班级过滤放在服务端，不能依赖前端隐藏入口来实现隔离。动机和业务范围见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 建立教师、学生两类角色的会话与授权边界。
- 将班级绑定到用户身份，并在服务端对材料和知识库查询统一追加班级约束。
- 提供教师上传、解析、入库和本班列表查询的最小闭环。
- 保证学生上传被拒绝，且拒绝路径不产生材料记录或知识库条目。
- 为后续检索问答和 AI 对话保留可复用的班级隔离知识库基础。

**Non-Goals:**

- 不设计注册、找回密码或自助加入班级流程。
- 不设计检索问答、AI 对话、作业提交与批改。
- 不规定具体前端框架、文件解析库或向量数据库；后续实现可按项目技术栈选择。

## Decisions

1. 服务端会话是权限来源。

   用户角色和所属班级必须来自服务端可信会话或服务端用户记录。上传、列表和材料详情接口均从当前会话推导 `userId`、`role`、`classId`，不接受客户端传入的班级标识作为授权依据。

   Alternatives considered: 让客户端传 `classId` 并由前端控制入口。该方案实现简单，但无法抵御参数篡改，不满足班级隔离要求。

2. 班级过滤集中在服务层或数据访问层。

   材料、知识库条目和后续可能扩展的材料详情读取都应通过统一的数据访问方法执行，并强制追加当前用户班级条件。直接按材料 ID 查询时，也必须同时匹配当前班级。

   Alternatives considered: 在每个页面或接口内单独拼接过滤条件。该方案容易遗漏，尤其在新增详情页或管理页时会产生跨班级读取风险。

3. 上传入库使用同一事务或等效的一致性边界。

   教师上传成功应产生材料记录和对应知识库条目；解析失败时不得展示部分入库结果。若解析过程耗时需要异步执行，材料记录应有明确状态，只有成功解析并入库后的材料进入可用列表。

   Alternatives considered: 先展示上传记录再慢慢补解析结果。该方案用户反馈更快，但在当前最小闭环中会模糊“列表查库展示”的验收口径。

4. 学生上传在入口和接口两层处理。

   前端可以隐藏学生上传入口以减少误操作，但服务端上传接口仍必须检查角色并拒绝学生请求。服务端拒绝是最终有效控制。

   Alternatives considered: 只在前端隐藏上传按钮。该方案不能防止直接调用接口。

## Risks / Trade-offs

- [Risk] 异步解析可能导致上传成功但列表暂时不可见。→ Mitigation: 若采用异步解析，材料状态必须区分处理中、失败、可用，并且本次验收只把可用知识库条目展示到本班列表。
- [Risk] 后续新增接口绕过统一班级过滤。→ Mitigation: 将班级过滤封装为共享服务或查询构造器，并为跨班级访问添加自动化测试。
- [Risk] 文件解析失败或恶意文件导致不完整入库。→ Mitigation: 解析失败时不发布知识库条目，并记录可审计的失败原因。
- [Risk] 班级归属变更影响历史材料访问。→ Mitigation: 本次按请求时的用户当前班级授权；若未来需要多班级或历史班级访问，应另开规约。

## Migration Plan

- 初始实现可直接创建所需表和接口，无需迁移既有业务数据。
- 若后续接入已有用户或材料数据，必须先补齐用户班级归属和材料班级归属，再启用受保护页面与列表接口。
- 回滚时应关闭上传入口和上传接口，保留已写入材料和知识库数据以便审计，避免误删用户上传内容。
