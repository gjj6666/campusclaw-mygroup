## Why

项目需要先建立账号登录、角色权限、班级数据隔离和教学材料入库的共同基础，否则后续功能会缺少可信身份边界和可验证的运行入口。把密码哈希、服务端密钥、Docker Compose 启动和健康检查一并纳入本变更，可以让最小系统从第一版起具备可部署、可检查、可审计的安全底座。

## What Changes

- 支持教师、学生使用账号密码登录；未登录访问受保护页面时引导到登录页。
- 密码 MUST 哈希存储，禁止明文保存或返回；登录验证 MUST 使用哈希校验。
- 密钥和敏感配置 MUST 仅来自服务端环境变量，不得写入前端代码或仓库明文配置。
- 实施角色权限：教师可以上传教学材料，学生调用上传接口必须被拒绝。
- 实施班级服务端隔离：A 班用户访问 B 班材料必须被拒绝，班级过滤不得依赖前端隐藏按钮。
- 教师上传材料后写入知识库，本班材料列表能够查询到对应记录。
- 提供 Docker Compose 启动方式，并提供 `GET /health` 健康检查接口。

## Capabilities

### New Capabilities

- `identity-access-control`: 覆盖账号密码登录、教师/学生角色、受保护页面访问控制、密码哈希存储和服务端环境变量密钥。
- `class-material-knowledge-base`: 覆盖班级作为数据边界、教师上传材料、学生上传拒绝、材料写入知识库和本班材料列表查询。
- `runtime-health`: 覆盖 Docker Compose 启动方式和 `GET /health` 健康检查。

### Modified Capabilities

- 无。

## Impact

- 影响用户、班级、材料、知识库条目的数据模型和迁移。
- 影响认证、会话、授权中间件、受保护页面路由守卫和上传接口。
- 影响材料解析、知识库写入、列表查询和服务端班级过滤。
- 影响应用配置、环境变量管理、Docker Compose 编排和健康检查端点。
- 需要覆盖密码哈希、未登录跳转、角色拒绝、跨班级拒绝、教师上传入库、本班列表可见、Compose 启动和 `/health` 响应的自动化验证。
